# 项目规则（CLAUDE.md）

> 本文件为通用模板（标准化部分）。复制到新项目后重命名为 `CLAUDE.md` 即可使用；工作进展与内容请记录在项目根目录的 `Claude_memory.md`（见「项目文档分工」）。初始化流程见 `template/README.md`。
> **模板版本：v4.3（2026-10-04）**，版本随模板变更递增（每次变更含新增整节 +0.1，仅章节结构性大改 +1.0），变更历史见模板母版工作区的 `Claude_memory.md`。
> **运行模式：团队制（默认总是组队）**——会话开局先装配团队（`lead` + `lit-agent` + `analysis-agent` + `figure-writer` + `auditor`），角色卡见 `team/roles/`、规则见「团队分工与协作」节；**未完成装配前不得开始检索、分析或出图**；用户明示「轻量/不组队」或环境不满足时按该节降级模式执行。
> **规则文件（v4.0 起）**：执行规则由总纲按 `<!--rules:…-->` 标记生成，成员只读 `team/rules/<角色>.md`（自包含，含通用规则）。生成：`scripts\build_rules.ps1`；校验（必须通过）：`scripts\build_rules.ps1 -Check`。**改总纲后必须重新生成并跑 `-Check`，未通过不得交卡。**
> **工作目录（v4.1 起）**：所有成员一律使用项目根的**绝对路径**；会话 cwd **不一定**是项目根（团队成员的 cwd 通常继承 `lead` 会话，可能落在母版或别处）。相对路径只在「已确认 cwd = 项目根」时使用；`scripts/` 下脚本自带项目根自检，不匹配即报错退出。
> **技能携带（v4.2 起）**：通用技能随 `skeleton/.dsh/skills/` 自动进项目（A 档），科研写作/制图技能随 `template/skills/` 携带、按需用 `scripts/install_skills.ps1 -Install` 安装（B 档）；清单与来源见 `.dsh/skills/VENDORED.md`。技能名**不带**命名空间前缀。

## 2. 文献支撑（与「文献检索记录与存档」相互配合）
> 主责：lit-agent ｜ 协作：lead ｜ 核验：auditor

- **所有论断引用支撑文献**：所有的方法学（methodology）、推理（reasoning）、观点（viewpoints）与解读（interpretations），必须引用参考支撑文献。
- **关键论断附带 PMID/DOI/链接**：每一条关键论断都应附带对应的 PubMed 文献来源（PMID / DOI / 链接）。
<!--rules:lit-agent-->
- **引用优先查本地文献库索引**：先从「文献检索记录与存档」的文献库索引（`literature/INDEX.md`）查找已有文献，找到即直接引用，无需重复调用 MCP 工具检索；每条引用都可回溯到对应的检索批次（CSV 文件）与检索策略记录，做到"引用有迹可循"。
- **索引查询细则（分级索引，控制 token 成本）**：文献库采用分级索引——`literature/INDEX_QUICK.md`（层级 1，仅分类小标题与篇数，小文件）与 `literature/INDEX.md`（层级 2，全量文献清单）。引用/检索前**先读层级 1** 判断主题覆盖情况：命中则按定位信息去层级 2 或 CSV 查细节；未命中才判定需要新检索。同一会话内层级文件各只读一次（**因文件系统写入前置校验等机制强制发生的重读不计入此约束**），读入后直接在上下文中复用，不重复读取；精确查找用 Grep 按 PMID/关键词定位，避免全量 Read；详细信息按需读取对应 CSV 条目。
- **同一主题只检索一次**：已检索过的主题不重复检索；仅在索引中确无相关文献时，才发起新的 PubMed 检索，且检索完成后必须按「文献检索记录与存档」更新文献库与索引。
<!--rules:common-->
- **证据等级标注**：引用时标注文献类型（系统综述/Meta 分析 / 原创研究 / 综述 / 病例报告 / 预印本），依据为标题、摘要与期刊信息（检索元数据或 DOI 解析）；无法确定时标注"证据等级未确定"，不得臆断。
- **引用用途标注**：每条引用标注用途（支撑 / 背景 / 对比）；不得将背景文献充当支撑文献。
- **转引规范**：凡未直接阅读原文的引用（仅见摘要或转述），必须标注"转引自 PMID xxx"，不得把转引内容当作原文引用。
- **时效性**：结论性论断优先引用近 5–10 年文献，前沿论断需近 3 年文献；经典奠基文献例外并注明其经典地位。
- **引用格式（统一）**：所有标注引用的地方统一使用格式 `[首作者名.年份; PMID:******]`，例：`[Small.2005; PMID:16028032]`；一条论断引用多篇文献时并列多个方括号，例：`[Small.2005; PMID:16028032][Orecchioni.2022; PMID:35025664]`；首作者名以检索返回的作者字段为准（取第一作者的姓，如 Small DM → Small）。
- 无法找到支撑的论断，应明确说明"未找到直接文献支撑"，不得含糊带过。
<!--rules:lit-agent,auditor-->
- **引用审计**：核查引用的真实性与匹配性——经 paper-search MCP 验证 PMID 真实存在，且对应文献确实支撑所论断的内容（必要时核对标题/摘要）；证据等级、引用用途、转引标注与实际一致；发现不实引用（PMID 不存在、张冠李戴、背景文献充当支撑）须更正并说明原因。

## 3. 事实真实性优先
> 主责：全体（各自产出） ｜ 核验：auditor

- **真实性第一**：事实真实性是第一位的，任何时候不得编造或臆测数据、文献、结论。
- **冲突以文献为准**：当文献内容与已有知识冲突时，以文献实际内容为准，并如实指出冲突。
- **不确定如实标注**：不确定的信息必须标注为不确定，不得以确定性语气陈述。

### 3.1 事实核查分级（按工具能力设计）

- **L1 摘要级（默认，自动执行）**：所有引用与摘录必须与检索返回的标题/摘要一致；摘要中明确出现的数值、比例、统计量可直接引用并注明"（源自摘要）"。
- **L2 全文级（按需执行）**：关键数值或方法学细节需要核实时，优先经 paper-search MCP 的 read_semantic_paper / download_with_fallback 走 OA（开放获取）途径获取全文核对。
- **L3 标注级（兜底）**：全文无法获取（如付费墙）时，如实标注"基于摘要，全文未核实"，或放弃该断言；不得用推测填充。
- **冲突文献并置呈现**：多篇文献结论冲突时，并列呈现并说明差异（模型、人群、方法等），不得只选取支持己方观点的文献。
- **AI 归纳标注**：对文献的归纳总结（非原文表述）需与摘要核对；跨文献综合结论需注明"综合自 PMID xxx, yyy"。

## 4. PubMed 访问方式
> 主责：lit-agent ｜ 核验：auditor

- **paper-search MCP 统一检索**：PubMed 检索统一使用 paper-search MCP 工具（已在全局配置，工具名带 `mcp__paper-search__` 前缀，如 search_pubmed、search_papers、read_semantic_paper 等），始终优先使用该工具，不使用第三方镜像或非官方接口。
- **检索覆盖 PubMed 全库**：检索范围不受文献开放获取（OA）状态影响，付费墙文献同样正常检索与收录（标题/摘要可得即可，收录与否则以相关性为准）；全文获取能力（read_semantic_paper / download 等）仅为可选增强，不作为收录标准。
- 检索时遵循 NCBI 使用规范（如 API key、限速要求）。
<!--rules:lit-agent,auditor-->
- **检索通道优先级与降级（MCP 优先 → 本地 CLI → 官方 HTTP 接口）**：检索按 **paper-search MCP → 本地 CLI（`paper-search.exe`）→ NCBI E-utilities 官方 HTTP 接口**（经 `web_fetch` 调用 esearch / esummary / efetch）的顺序取用，**上级通道可用即不得降级**；**任何降级都必须在检索策略文件的「工具与来源」中如实登记**（降级链、实际调用的 URL 与关键参数、调用时间、返回条数），不得静默改道；**禁止使用镜像或非官方接口**；授权通道全部不可用时**停下并升级**（成员经 `lead` 上报用户），不得自行改道或凭印象补全文献信息。

<!--rules:lit-agent-->
## 5. 文献检索记录与存档
> 主责：lit-agent ｜ 协作：lead（归档总控）

- 每次 PubMed 检索后，必须将检索结果归档，包括：
  - **文献信息 CSV 列表**：保存本次检索到的文献主要信息（字段：检索序号、PMID、标题、作者、期刊、年份、DOI、PubMed 链接、核心结论摘要），保存为 UTF-8 编码的 CSV 文件（建议同时存一份 UTF-8 BOM 版本以便 Excel 直接打开）。
  - **检索策略记录**：保存本次检索的策略（检索目的、检索式、使用的工具与来源、检索时间、返回结果数、筛选/收录说明），保存为 Markdown 文件。
  - **按顺序保存**：文件名以 `日期_序号` 前缀命名（如 `2026-08-01_01_xxx.csv`、`2026-08-01_01_xxx.md`），序号随检索次数递增，禁止覆盖或删除历史记录。
- 设立专门子目录 `literature/` 管理文献（**分级索引**）：
  - `literature/INDEX_QUICK.md`：**层级 1 快速索引**，仅含分类小标题、各子主题篇数与定位信息（小文件），供「文献支撑」节引用/检索前先读以判断主题覆盖
  - `literature/INDEX.md`：**层级 2 全量索引**，汇总全部检索批次与文献明细（PMID、标题、年份、标签、来源批次），是本地文献库的完整入口
  - `literature/csv/`：文献信息 CSV 列表
  - `literature/search_strategy/`：检索策略记录
  - **每次新增检索后必须同步更新分级索引**：在 `literature/INDEX_QUICK.md`（层级 1）追加新分类与篇数，在 `literature/INDEX.md`（层级 2）追加新批次条目（主题、日期、文献数、CSV/策略文件路径）与文献明细，保证两级索引始终反映文献库全貌，逐步搭建项目独有的文献库。
- **检索覆盖角度**：每个主题至少用 2 个以上不同角度的检索式（如不同关键词组合、不同子方向），避免单一检索式漏检；角度在策略记录中列明。
- **阴性检索结果归档**：检索无有效结果（返回 0 条或全部不相关）时，同样记录到检索策略文件（标注检索式与阴性结论），并在 `INDEX_QUICK.md`「已知空白」区登记主题词，避免后续重复检索同一主题。
<!--rules:lit-agent,auditor-->
- **检索策略记录须落盘候选池（可逐条回溯）**：每次检索必须随检索策略文件落盘**候选池**——本次取回的**全部 PMID** 与**去重后的唯一 PMID 清单**，并标明各条来自哪个查询/通道，使"某条 PMID 从哪一步来"（哪个检索式、哪条通道、第几轮筛选）可直接回溯；审查方据此**逐条比对**收录与去重结果。候选池不落盘时，审查只能靠重跑检索推断等价性——既不可逐条核验，也无法解释重跑差异。
- **原始响应与中间凭证的生命周期（v4.1 新增，必须声明）**：原始响应（HTTP 正文、`_tmp_*`／spill 临时文件）与中间凭证的**保留期限与删除时点**须由 `lit-agent` 决定，并**在检索策略文件中显式声明**。若交付前已删除，必须写明「原始响应已删除，追溯依据为落盘候选池与调用登记清单」，并声明由此产生的局限（**无法重放当时的响应正文**）。审查方须在报告中登记该限制，不得据此推断"不存在未登记调用"。

## 6. 产出与维护规范
> 主责：lead（交付自检） ｜ 核验：auditor ｜ 引用核验脚本：lit-agent

- **术语表**：建立并维护 `literature/glossary.md` 中英术语对照表；正文中术语首次出现时用"中文（English）"格式；产出中新出现的术语需同步更新术语表，保证全文翻译一致。
<!--rules:common,lead-->
- **交付自检**：重要产出（综述、调研报告、正式文档）交付前自检：①每条关键论断均有 PMID 且可回溯到检索批次；②数值已按「事实核查分级」分级核查；③证据等级与引用用途已标注；④术语表一致；⑤冲突与不确定之处已如实标注。
<!--rules:common,lead,auditor-->
- **引用可回溯性脚本化核验**：交付自检的引用核验可（且建议）脚本化——自动检查正文全部 PMID 均存在于 `literature/INDEX.md`、参考文献列表与正文引用一一对应（无遗漏无多余），输出核对报告；不得仅凭目测判断引用完整。
<!--rules:common-->
- **引用格式**：对话、笔记、文献库内部与正式文档正文中，所有引用统一按「文献支撑」节格式 `[首作者名.年份; PMID:******]` 标注；正式文档（论文、报告）的参考文献列表按目标期刊格式另行输出。
- **数据与伦理合规**：若课题涉及临床或受试者数据，须遵守伦理审批与去标识化要求，产出中不出现可识别个体信息。

## 7. 工具与资源复用规范
> 主责：analysis-agent ｜ 审计：auditor

- **复用优先级（自高到低，不得跳级）**：本节为**通用规则**，适用于项目内**一切**新工具/新算法的获取与复用，不限于生信分析。项目需要新工具或新算法时，按以下顺序获取：
  1. **项目内已有**：查询 `tools/tools.csv` 与项目目录，存在同类工具则直接复用；
  2. **开源成熟项目**：经 GitHub MCP 检索（`mcp__github__search_repositories` 搜仓库、`search_code` 搜代码），选用成熟项目直接复用；
  3. **自行实现**：仅当上述两级均无可用工具时，方可考虑自行实现；**决定自行实现前须停下请示用户，经用户同意后方可开始**。
- **候选评估**：对每个候选项目评估：成熟度（star 数、最近更新时间、维护活跃度）、license 合规性、文档质量、可复用性（接口/CLI 清晰、依赖轻）；评估依据如实记录，不凭印象选用。
- **来源记录（tools.csv）**：每次复用新工具，将工具信息追加至 `tools/tools.csv`（字段：序号、日期、工具名、简介、仓库链接、版本、license、评估结论）；历史保留、不覆盖，可追溯性与文献 CSV 一致。
- **来源审计**：核查 `tools/tools.csv` 中记录的真实性——经 GitHub MCP 验证仓库存在且链接可访问，工具名、版本、license 与仓库实际信息一致，评估结论与实际情况相符；发现不符须更正记录并在原条目注明；生信场景下与「生信算法脚本规范」的子 agent 审查一并执行。

## 8. 生信算法脚本规范
> 主责：analysis-agent ｜ 独立审查与重算：auditor

- **适用范围**：本节仅规范**生信分析工作**（算法选择、脚本实现、结果审查）的方法与质量要求，不影响其他工作；其中工具的获取与复用服从「工具与资源复用规范」（通用规则）。
- **分析设计先行（superpowers 流程）**：正式分析开始前，先按 `brainstorming` 的规划流程与用户讨论设计分析方案，**设计期间须完成并写入计划书**：①确定标准方法——先查询 bio 系列 skill（正式名 `bio-*`，如 `bio-single-cell-preprocessing`、`bio-differential-expression-deseq2-basics`、`bio-variant-calling-gatk-variant-calling`）是否有该分析的标准方法，有则直接采用；无则经 **paper-search MCP 检索支撑与范式文章**（方法学原始文献 / 权威综述 / 方法学指南），据此确定**方法学与参数**（**方法由文献确定；实现工具的获取与复用按「工具与资源复用规范」经 GitHub MCP 检索**），不凭经验或印象编造；②确定运行策略——预估 ≤1 分钟的任务可直接正式运行，否则必须小样本预跑；③方案四要素（输入数据、分析方法与流程、预期输出、验证计划）。计划书经用户批准后，方可进入实现与运行阶段，未经批准不得动手。
- **小样本预跑（正式运行前必做）**：正式运行前，须先用小样本/小数据测试运行整个流程：①验证输入端格式与内容无问题；②确认脚本无误（无报错、参数正确）；③核对输出结果正确；④预跑阶段同样执行审计（子 agent 独立审查、关键统计量独立重算）；预跑全部通过后，方可正式运行。**小样本规模**：约为正式数据的 1%–5%；下限为能覆盖全部输入列/分组结构的最小规模，上限以预跑能在约 1 分钟内完成为准。
<!--rules:common,analysis-agent-->
- **异常升级**：执行过程中，若结果与计划书预期重大不符，或出现计划书未覆盖的情况，须停下请示用户，由用户决定调整方向；不得自行修改方案、扩大范围或继续推进。
<!--rules:analysis-agent,auditor-->
- **子 agent 独立审查（自检）**：每一部分（数据处理、算法实现、结果生成等）完成后，启用独立的子 agent 进行审查；审查**不依赖工作记录与注释**，只检查脚本与结果本身的真实性、可靠性——是否存在 AI 幻觉式拟合（编造数据、硬凑结果、结论与数据不符），确保事实真实性（与「事实真实性优先」节一致）。**审查结论须归档**到独立的 `review/` 子目录：一级子目录按审查对象（数据处理、算法实现、结果生成等）划分，文件名 `日期_序号_状态.md`（序号递增，不覆盖历史）；**状态三态标注「通过 / 未修复 / 已修复」，文件名后缀 + 文件头部显著标记双保险**；问题修复后须更新记录内容并重命名文件（`_未修复` → `_已修复`），保证扫一眼目录即知哪一部分、第几次、是否已修复，审查全程可追溯。
<!--rules:auditor,analysis-agent-->
- **关键统计量独立重算**：审查关键统计量（p 值/FDR、相关性、富集、效应量等）时，须从**原始数据独立重算**并与结果文件对比（不得直接调用项目自带审计脚本——审计脚本与生成脚本同源，可能"自洽但整体错误"）；独立重算与结果一致才判「通过」，不一致须定位原因并归档至 `review/`。
<!--rules:analysis-agent-->
- **工具获取服从通用规则**：生信分析所需的工具获取与复用，统一服从「工具与资源复用规范」（通用规则），本节不重复。

## 9. 作图规范
> 主责：figure-writer ｜ 像素级验证复核：auditor

- **作图前先读源文件**：开始作图前，必须先读取用于可视化的原始结果文件（统计输出、分析结果表等）与生成该结果的脚本，明确数据来源与结构后再作图；不得在未读源文件的情况下凭印象出图。
- **输出与来源对应命名**：可视化输出文件按规范命名，与来源脚本/结果文件一一对应（如 `fig1_主题.svg/.png` 对应脚本 `fig1_主题.R` 及其结果文件），保证每张图可回溯到产生它的脚本与数据。
- **出图规划先行（superpowers 流程）**：出图与改图前，先按 `brainstorming` 的规划流程与用户讨论确定出图规划——图的数量（**以尽可能少的图说明结果**）、顺序、每张图说明什么结论；并明确区分**主图（正文）与附录附加图**；规划确定后再动手。
- **一图一张，不拼图（v4.1 明确边界）**：**每张图单独成文件**——不得把**结论不同**的多张图拼入同一文件，也不得用 `patchwork` / `gridExtra` / 多列 `facet` 等把彼此独立的图表合成一图。**面板（panel）与图的关系**：**同一结论**下的多面板图**允许**，但须同时满足 ①面板数 ≤3；②在出图规划中声明面板构成与每个面板各自的子结论；③面板用字母标号，图注逐面板说明。若某面板可独立表达一个结论且能被单独引用，则应拆为独立单图。**单面板图不得带字母标号**。只输出 **SVG 与 PNG** 两种格式；图片四周留白宽裕（**判据：四边最外 8 px 行/列的非背景像素数 = 0**，实测 4 mm ≈ 47 px 外边距即可满足），确保坐标轴标签、图例、刻度、标题等任何要素互不重叠。
  > 说明（2026-10-01 实弹测试实证）：原措辞「禁止多图拼接组合（不合并子图）」未区分"文件级拼接"与"面板"，按字面执行会把科研论文最常见的多面板主图判为违规（本轮实测：2 张 3 面板图被判违规并拆成 6 张单图，同时与同节「以尽可能少的图说明结果」互斥）。本版据此明确边界。
- **配色统一**：配色按三类场景选择——单色（灰度）、双色（红蓝）、多色；同一产出（论文/报告）内风格必须统一；选用**低饱和、高对比**、有使用先例的配色方案，不自行发明高饱和撞色。
- **R 语言出图**：出图与改图一律使用 `nature-figure` skill 完成（技能名**不带命名空间前缀**），作图语言固定为 **R**，不混用其他语言。
- **内容精简**：图内文字尽量少（标题、标签、注释能省则省）；不使用底纹背景；不加图内辅助线（网格线、参考线等），只保留传达结论所必需的要素。
<!--rules:figure-writer,auditor-->
- **像素级验证（强制，导出后必做）**：每张图导出后必须进行像素级验证——用脚本（如 Python PIL）扫描输出文件，确认关键配色像素数 > 0、图非空白，再做目检；**不得仅凭目检/预览判断图已正确渲染**（目检存在视觉误差，曾出现"空白图被误判为正常"的事故）。
- **规避渲染陷阱**：ggplot2 图层的颜色（fill/colour）一律用数据框 + aes 映射 + `scale_fill_identity()`/`scale_colour_identity()` 写法；**不得在循环内引用 `aes(x[i])`**（aes 惰性求值，循环索引到绘图时才解析，所有图层会堆叠到最后一个索引）；ggforce::geom_shape 等包在本机可能存在 fill 不渲染的兼容问题，遇异常先做最小渲染实验定位。
- **版本分文件夹**：多版本迭代产出（图、脚本、文档、手稿、审查报告）按版本分子目录保存（`v1/`、`v2/`…），新版本不与旧版本混放；旧版本按历史只读保留、不清理不修改，避免新旧混淆与误用。**首次产出即落 `v1/`**，不要先写在目录根、等迭代时再回填（实测：先落根目录会造成"首版无版本目录"的空白，迭代时须额外搬运并解释）。
- **图数据核对**：绘图数据若经导出脚本生成，导出后必须与原始结果文件核对（数值、基因/条目列表、样本数等），防止导出环节引入数据源错误（曾发生图误用历史模块数据源的事故）。

## 10. 写作手稿规范
> 主责：figure-writer ｜ 引用完整性核验：auditor

- **写作技能**：手稿起草与改写一律调用 `nature-writing` skill 完成（技能名**不带命名空间前缀**）。
- **仅中文输出**：手稿只输出中文；术语按「产出与维护规范」节术语表用"中文（English）"格式。
- **双格式保存**：交付时同时保存 Markdown（.md）与 Word（.docx）两种格式，注意排版（标题层级、段落、表格、图注在两种格式中均规范呈现）。Word 格式经 **python-docx** 库生成；环境未安装时自动执行 `pip install python-docx` 完成配置后再转换，不得以"未安装工具"为由跳过 Word 交付。
- **先结构后全文（两段式）**：第一次调用不写完整文稿，先给出**主线与大小标题**（目录式结构），明确写作逻辑而非具体内容；经用户修订后得到一版确定的大小标题结构；依此再次调用 nature-writing 与用户**讨论结构优化问题**，定稿后再写全文。
- **引用与插图完整**：全文引用按「文献支撑」节格式标注、参考文献完整可回溯（对应检索批次）；插图按「作图规范」节产出，逐一插入对应位置并配图注，不得缺图漏图。

## 12. 团队分工与协作

- **技能的获取与安装（v4.2）**：A 档技能随 `skeleton/` 自动进项目；B 档技能随 `template/skills/` 携带，按需用 `scripts/install_skills.ps1 -Install` 安装（默认从 `<项目根>\template\skills` 取源，模板包不在项目内时用 `-Source` 指定）。引用与工具来源的真实性核验走 **PubMed MCP / GitHub MCP**。

### 12.1 团队铁律（原 team/README.md，迁入以避免两处规则）

1. 交接只认**落盘文件 + 任务卡**，不认消息；消息只用于唤醒与提问。
2. `inactive` ≠ 完成；收卡必须**实际核对产出物存在**。
3. **任务就绪不唤醒 owner**，lead 必须显式唤醒下游。
4. **owner 不自动释放**：成员崩溃后卡仍是 in_progress，lead 必须 reassign/release。
5. **审查者必须 `fresh`**，禁止 `fork`（会把 lead 的推理带进去）。
6. 名字永久不复用，本机上限 8（含失败成员）：固定 4 名 + 备名 2 个，余量只用于重建。
7. git 操作由 lead 独占，其他角色只读 `git status` / `git diff`。
8. 审查期间**冻结被审文件**；确需修改须通知审查者对新版本重新取证，审查报告登记被审文件哈希。
9. `lead` 重开上游卡时**必须同时处理下游卡**——机制不会撤销下游已有的认领（实测：上游 reopen 后下游仍 in_progress 且保留 owner）。
10. 本机**同时活跃成员上限 3**（「成员总数上限 8」是另一回事）→ 4 名成员须错峰唤醒。
11. **每收一张卡提交一次**，commit message 以「卡 id + 角色」开头（如 `C-03 analysis-agent: …`）；同机同用户下 git author 无法区分成员，卡级归属只能靠提交信息。
12. 任务卡的验收标准若涉及**数值、计数或条目数**，必须写明**精度与舍入口径**（如"AUC 与权威值之差 < 1e-6"还是"四舍五入到 3 位后相等"；"共 5 条"还是"逐条照录、不得增删"）。实测教训两条：① 上游产出把 AUC 存为 3 位小数时，字面判据"差 < 1e-6"永远不可达，会让执行者卡在一个无法满足的条件上；② 建卡时写「结果须含计划书 §7 的**五条**局限」而上游文件实为 **4 条**，执行者被迫自行解释并额外声明差异——**引用上游文件的条目数时，一律写「逐条照录，不得增删」，不要硬编码条数**。
13. 像素/颜色断言用**精确匹配**而非容差匹配：实测灰字 `rgb(96,96,96)` 与配色 `#4F5D6B` 的最大通道差仅 17，容差 ≤24 会把 3531 个抗锯齿像素误判为命中。
